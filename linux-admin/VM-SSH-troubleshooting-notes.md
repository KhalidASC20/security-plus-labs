# Troubleshooting a Broken SSH Key Authentication Setup (Multi-Layered Root Cause)

**Date:** September 2026

**Tools used:** VirtualBox, Ubuntu Server, PowerShell, OpenSSH

**Environment:** Personal Ubuntu Server VM, accessed remotely from my own laptop

### Objective

Configure SSH key-based authentication on a freshly installed Ubuntu Server VM, then disable password authentication entirely to harden remote access — standard first-day server hardening steps.

### Steps taken (and the problems encountered at each layer)

1. Generated what I believed was an SSH key pair during initial setup — later discovered this was run inside the VM's own console session instead of on my laptop (the actual client), meaning no real key pair existed on my laptop at all.
2. Attempted to disable `PasswordAuthentication` in `/etc/ssh/sshd_config`, following standard guidance — but logins continued to prompt for a password despite the change.
3. Investigated using `ls /etc/ssh/sshd_config.d/` and discovered a separate override file, `50-cloud-init.conf`, auto-generated by Ubuntu's cloud-init during installation. Files in this directory are loaded before the main config and take precedence — my edit to the main file was being silently overridden.
4. Edited the override file to match, restarted the SSH service, and re-tested — but was met with `Permission denied (publickey)`, since password authentication was now genuinely disabled everywhere, and no valid key existed to replace it.
5. Diagnosed the missing key by checking `~/.ssh/id_ed25519.pub` on my laptop directly — confirmed the file did not exist, consistent with the key having been generated in the wrong location (the VM) in Step 1.
6. Temporarily re-enabled `PasswordAuthentication` in both configuration locations to restore a valid login path while the key issue was resolved.
7. Generated a proper key pair on my laptop this time, and confirmed its existence and content directly.
8. Attempted to use `ssh-copy-id` to push the new public key to the VM, and discovered this utility is not included with Windows' native OpenSSH client — it is a Linux/Mac convenience script with no PowerShell equivalent.
9. Used a manual equivalent instead, piping the local public key's contents through an SSH session and appending it directly to the VM's `authorized_keys` file: `type $env:USERPROFILE\.ssh\id_ed25519.pub | ssh user@host "cat >> ~/.ssh/authorized_keys"`.
10. Verified the correct key now matched between laptop and VM, and confirmed successful key-based login with no password prompt, in a fresh terminal session, before touching any configuration further.
11. Only after confirming key-based login worked reliably, re-disabled `PasswordAuthentication` in both configuration files a final time, restarted SSH, and re-verified access in a new session before considering the task complete.

### What I found

The root cause was a chain of three separate, compounding issues rather than a single mistake: (1) the SSH key pair was generated in the wrong location (the VM console rather than the laptop client), producing no usable client-side key; (2) Ubuntu's `sshd_config.d/50-cloud-init.conf` override file silently took precedence over edits made to the primary `sshd_config`, a configuration-precedence behavior that isn't obvious from the main config file alone; and (3) the standard `ssh-copy-id` convenience tool assumed by most tutorials is unavailable on Windows PowerShell by default, requiring a manual workaround.

Disabling password authentication before verifying key-based access actually worked created a genuine, temporary lockout condition — recoverable here only because a separate, already-authenticated console session to the VM had deliberately been kept open throughout the process.

### Why it matters (the security angle)

This directly demonstrates a core operational risk in access-control hardening: removing a fallback authentication method (password) before confirming its replacement (SSH key) is fully functional can immediately and completely lock out legitimate access. Real-world system administrators guard against exactly this scenario by maintaining an out-of-band access path (in this case, a separate console session) before making authentication changes to a remote-only access method — a practice this exercise validated firsthand rather than just conceptually.

This also demonstrated a genuine, non-obvious Linux configuration-management concept: **include-file precedence**. Modern Linux systems increasingly split configuration across a main file plus a directory of override snippets (sshd_config.d/, and similarly sudoers.d/, systemd drop-in directories, etc.), specifically so automated tools like cloud-init can apply settings without directly modifying hand-maintained config files. Understanding that an override directory can silently take precedence over an edited main file is a genuinely useful, transferable troubleshooting instinct beyond just SSH.

### next steps

- When hardening remote access controls in the future, always verify the replacement authentication method in a separate, still-open session before disabling any fallback method — never assume success without confirmation in a fresh connection.
- When a configuration change appears to have no effect, check for override/include directories before assuming the edit itself was wrong.
- Next step: install VirtualBox Guest Additions to enable clipboard sharing between host and VM, since troubleshooting via manual re-typing (rather than copy/paste) significantly slowed diagnosis during this exercise — a good reminder that basic tooling/environment setup affects troubleshooting speed as much as technical knowledge does.
